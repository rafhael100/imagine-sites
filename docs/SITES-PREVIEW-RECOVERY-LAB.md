## Ensaio preparado (SQL NÃO EXECUTADO)

`tests/run-preview-recovery.sh` cria dois clusters próprios em um diretório 0700 aleatório `/tmp/sites487-recovery-*`, initdb com PG18 já disponível, logins bootstrap distintos, senhas bootstrap e runtime aleatórias, distintas por cluster e privadas e portas loopback fixas 55450/55451. Não há socket público, fallback de porta, instalação ou uso de servidor existente. A configuração Laravel efetiva e identidade SQL (banco postgres, login/session actor, cluster, diretório, versão, endereço e porta) são comparadas antes de qualquer role/migration. Cluster, diretório, login e porta devem ser independentes. O harness recusa origem/destino trocados e ID esperado de origem incorreto, usando identidades SQL relidas, antes de preparar os fixtures.

Apenas a origem recebe a migration real existente. Reutiliza a matriz de fixtures #487: owner `lab486_owner` NOLOGIN/NOBYPASSRLS, seis logins autor/revisor/leitor separados por duas empresas. O destino recebe somente os mesmos papéis sintéticos sem privilégios de produto antes do restore; seus grants são recuperados do dump. Não se exportam senhas/globals reais.

Dados: dois projetos, quatro versões com briefing/HTML/SHA, duas revisões approved_internal, oito eventos de auditoria e seis principals. Revoga-se um leitor na origem antes da cópia. Depois da preparação a conexão da origem fica read-only, bem como todos os comandos de dump. Nenhuma restauração aponta para origem. As contagens esperadas são exigidas antes de exportar.

`pg_dump --schema=sites_preview --format=custom` inclui todas as tabelas, funções, sequência, constraints, triggers, policies, owners e ACLs do namespace atual. Drift no inventário de tabelas interrompe o ensaio. `pg_restore --single-transaction --exit-on-error` restaura apenas em destino ainda vazio, após nova validação de ambas as identidades, manifesto da origem, esquema e SHA do arquivo. Não usa clean/create/no-owner/no-acl/disable-triggers. Papéis são pré-criados porque dumps de schema não incluem globals. Não é backup do banco completo nem do ledger Portal.

Readback exige igualdade dos hashes SHA256 de linhas ordenadas de cada tabela, cardinalidades, estado da sequência e SQL completo do esquema; só se removem as chaves aleatórias psql restrict geradas por pg_dump para comparar esquema. O arquivo dump também tem SHA256 registrado (integridade local, não assinatura/custódia independente). A origem é relida para demonstrar que permaneceu igual. Logins restaurados validam runtime não privilegiado, leitura da própria empresa/digests de ambas as versões, recusa de leitura cruzada, capacidades autor/revisor/leitor, recusa do leitor revogado e ausência de revisão herdada na versão 2. ## Execução futura em laboratório já autorizado

Pré-requisitos: PHP CLI 8.3+ com PDO pgsql/posix, dependências Composer de `apps/sites`, binários existentes de uma mesma distribuição oficial PG18 (`initdb`, `pg_ctl`, `pg_controldata`, `pg_dump`, `pg_restore`). Nenhuma instalação de dependência é feita por este runner. Portas 55450/55451 precisam estar livres; startup falha sem substituir serviços. Não execute no ambiente atual que já recusou socket.

```bash
env -i PATH=/usr/bin:/bin PHP_BIN=/caminho/php PHP_INI=/caminho/ini-revisado \
  PG_BIN=/caminho/postgresql/18/bin SITES_LOCAL_RECOVERY=1 \
  /bin/bash --noprofile --norc tests/run-preview-recovery.sh
```

Exigir saída zero e todos os marcadores: `NEGATIVE PREFLIGHT OK`, `PREFLIGHT OK`, `MANIFEST OK`, `ARCHIVE SHA256`, `SCHEMA SHA256`, `RECOVERY OK`. O runner exige o último marcador explicitamente. Saída bruta de servidor/initdb/stderr de ferramentas é descartada; console mostra somente marcadores e estágio sanitizado, nunca senha/PDO erro. `manifest.json` e `result.log` registram a prova se houver êxito. O trap valida raiz, PGDATA, cluster ID e, se ativo, PID/diretório/porta/executável próprio; tenta parar ambos mesmo com falha e agrega resultados. Só após confirmar ambos inativos remove os arquivos exatos de senhas/pgpass/dump, validando UID/modo/link. Preserva manifesto/log sanitizado e os diretórios privados de cluster inativos (estes não são artefatos publicáveis e contêm dados sintéticos). Falha de cleanup preserva arquivos privados para decisão, retorna erro e não amplia a limpeza. Não mudar porta/permissão/sandbox.
